# Vehicle Report Card Navigation and Odometer Correction Design

## Objective

ปรับหน้ารายงานตรวจรถให้เริ่มจากการ์ดเมนูแบบ Grid จำนวน 5 ใบ ผู้ใช้เลือกเปิดรายงานเป็นหน้า ๆ และระบบโหลดรายละเอียดเฉพาะเมื่อผู้ใช้กำหนดช่วงเวลาแล้วกดแสดงรายงาน พร้อมเพิ่มช่องทางแก้เลขไมล์ที่กรอกผิดโดยจำกัดสิทธิ์และเก็บประวัติครบถ้วน

## Confirmed Decisions

- เมนูหลักประกอบด้วย `สรุป`, `รายวัน`, `รายเดือน`, `น้ำมัน` และ `จัดการข้อมูล`
- เมนูทั้ง 5 รายการแสดงเป็นการ์ด Grid แยกใบ ไม่ใช้แถบเลื่อนแนวนอน
- Desktop แสดง 5 ใบในแถวเดียว, Tablet แสดง 3+2 ใบ และ Mobile แสดง 2+2+1 ใบ
- คลิกการ์ดแล้วแสดงเนื้อหาของหมวดนั้นเพียงหมวดเดียว
- หน้ารายงานไม่โหลดหรือแสดงรายละเอียดจนกว่าจะเลือกช่วงเวลาและกด `แสดงรายงาน`
- `จัดการข้อมูล` ไม่บังคับเลือกช่วงเวลา เพราะเป็นหน้าจัดการรถและคนขับ ไม่ใช่รายงานตามวันที่
- แก้เลขไมล์ได้เฉพาะผู้ใช้ role `admin` หรือผู้ใช้ role `accounting` ที่มีอีเมล `acc.ap@hillkoff.com`
- ฝ่ายขายและบัญชีอื่นอ่านรายงานได้ตามสิทธิ์เดิม แต่แก้เลขไมล์ไม่ได้

## User Interface

### Menu Grid

การ์ดแต่ละใบประกอบด้วยไอคอน ชื่อหมวด และคำอธิบายสั้น การ์ดที่เลือกใช้สีเขียวและมีสถานะ `aria-selected=true` ส่วนการ์ดอื่นใช้พื้นสีขาวและมีเส้นขอบชัดเจน การจัดวางต้อง wrap ตามขนาดหน้าจอโดยไม่เกิด horizontal scrolling

หน้าเริ่มต้นแสดง:

1. Hero ของรายงานตรวจรถ
2. การ์ดเมนู Grid
3. ข้อความแนะนำให้เลือกหมวดรายงาน

หน้าเริ่มต้นต้องไม่แสดงตัวกรอง ตารางรายละเอียด การ์ดตัวเลขสรุป หรือข้อมูลการใช้รถ

### Report Pages

เมื่อเลือก `สรุป`, `รายวัน`, `รายเดือน` หรือ `น้ำมัน`:

1. แสดงชื่อหน้าที่เลือก
2. แสดงตัวกรองวันที่เริ่มต้น วันที่สิ้นสุด รถ และคนขับ
3. แสดงปุ่ม `แสดงรายงาน`
4. ก่อนกดปุ่ม แสดง empty state และไม่เรียก API รายงาน
5. เมื่อกดปุ่มและข้อมูลวันที่ถูกต้อง จึงเรียก API และแสดงข้อมูลเฉพาะหมวด

เมื่อผู้ใช้เปลี่ยนหมวดหรือแก้ตัวกรอง รายงานเดิมต้องถูกทำเครื่องหมายว่ารอตรวจสอบใหม่ และไม่ถือว่าข้อมูลเก่าตรงกับตัวกรองใหม่จนกด `แสดงรายงาน` อีกครั้ง

ผลลัพธ์ของแต่ละหน้า:

- `สรุป`: การ์ดตัวเลขสรุป คุณภาพการเชื่อมข้อมูล และรายการภาพรวมตามช่วงเวลา
- `รายวัน`: ตารางการใช้รถรายวัน เลขไมล์ ระยะทาง คนขับ และจำนวนออเดอร์
- `รายเดือน`: ผลรวมรายเดือนของออเดอร์ ระยะทาง และค่าน้ำมัน
- `น้ำมัน`: รายการเติมน้ำมันและยอดรวมตามช่วงเวลา
- `จัดการข้อมูล`: รถ ผู้ครอบครองทรัพย์สิน และคนขับ พร้อมการเพิ่ม แก้ไข และปิดใช้งานตามสิทธิ์เดิม

### Loading, Empty, and Error States

- ระหว่างโหลด ปิดปุ่ม `แสดงรายงาน` และแสดงสถานะกำลังโหลด
- ถ้าไม่มีข้อมูล แสดงข้อความว่าไม่พบข้อมูลในช่วงเวลาที่เลือก
- ถ้า API ล้มเหลว เก็บตัวกรองเดิมไว้และแสดงข้อความผิดพลาดพร้อมปุ่มลองใหม่
- ตรวจว่าจากวันที่ไม่เกินถึงวันที่ก่อนส่งคำขอ

## Odometer Correction

### Entry Point

หน้ารายวันและรายการภาพรวมในหน้าสรุปแสดงปุ่ม `แก้เลขไมล์` เฉพาะเมื่อผู้ใช้มีสิทธิ์แก้ไข รายการที่เลือกต้องระบุ event ต้นทางของเลขไมล์เริ่มและสิ้นสุดได้อย่างชัดเจน ไม่แก้จากค่ารวมที่ไม่มี reference ไปยังเอกสารต้นทาง

### Edit Form

หน้าต่างแก้ไขแสดง:

- วันที่ใช้งาน
- รถและทะเบียน
- คนขับ
- เลขไมล์เริ่มต้นเดิมและช่องค่าใหม่
- เลขไมล์สิ้นสุดเดิมและช่องค่าใหม่
- เหตุผลในการแก้ไขซึ่งบังคับกรอก

Validation:

- ค่าเลขไมล์ต้องเป็นตัวเลขมากกว่า 0 และไม่เกิน 10,000,000
- เลขไมล์สิ้นสุดต้องไม่น้อยกว่าเลขไมล์เริ่มต้น
- ต้องมี event ต้นทางที่ยังอยู่ในระบบ
- เหตุผลต้องไม่เป็นค่าว่าง

### Authorization

UI แสดงปุ่มแก้ไขเมื่อ:

```text
role === "admin"
OR
(role === "accounting" AND normalizedEmail === "acc.ap@hillkoff.com")
```

API ต้องตรวจเงื่อนไขเดียวกันจาก token และ profile ทุกครั้ง การซ่อนปุ่ม UI ไม่ถือเป็น authorization

### Server Update and Audit

เพิ่ม server API สำหรับแก้ไขเลขไมล์ โดยทำงานใน Firestore transaction:

1. อ่าน event ต้นทางและตรวจว่ายังมีอยู่
2. ตรวจสิทธิ์ผู้ใช้
3. ตรวจค่าใหม่และความสัมพันธ์ของเลขไมล์ต้น–ปลาย
4. บันทึกค่าใหม่ลง `vehicle_usage_events`
5. บันทึก audit record ที่มี event ID, ค่าเดิม, ค่าใหม่, เหตุผล, UID, อีเมล, role และเวลา
6. ส่งผลลัพธ์ที่แก้แล้วกลับให้ UI

ข้อมูล audit ใช้ collection `vehicle_odometer_audits` และห้ามให้ client เขียนโดยตรง

หลังแก้สำเร็จ UI เรียกโหลดรายงานใหม่ด้วยหมวดและตัวกรองเดิม เพื่อให้ระยะทางและผลรวมคำนวณจากข้อมูลล่าสุด

Google Sheets sync เดิมต้องไม่ถูกเขียนแบบ append ซ้ำโดยอัตโนมัติในงานนี้ การแก้ production source of truth อยู่ที่ Firestore พร้อม audit; การปรับ reconciliation กับ Google Sheets เป็นงานแยกหากต้องการในอนาคต

## Data Contract Changes

ผลลัพธ์รายงานรายวันต้องเพิ่ม reference ที่จำเป็นต่อการแก้ไข:

- `odometerStartEventId`
- `odometerEndEventId`
- ค่าเลขไมล์ต้นและปลายที่คำนวณแล้ว

ไม่มี migration แบบ bulk เอกสารเก่า รายการที่หา event ต้นทางไม่ได้ยังอ่านรายงานได้ แต่ไม่แสดงปุ่มแก้ไขและแสดงสถานะว่าแก้ผ่านหน้านี้ไม่ได้

## Security and Compatibility

- บัญชี `accounting` ยังคงไม่มีสิทธิ์อ่านหรือเขียน Firestore โดยตรง
- ทุกการอ่านรายงานและแก้เลขไมล์ผ่าน server API
- ไม่เปลี่ยน flow ที่คนขับบันทึกการใช้รถ ตรวจรถ หรือเติมน้ำมัน
- ไม่แก้ข้อมูลออเดอร์ น้ำมัน รายงานตรวจรถ หรือ master data ระหว่างแก้เลขไมล์
- ไม่ขยายสิทธิ์แก้เลขไมล์ให้ฝ่ายขาย
- API query เดิมยังรองรับ role `sales`, `admin` และ `accounting`

## Testing and Verification

### Unit Tests

- หน้าเริ่มต้นมีการ์ด Grid 5 ใบและไม่ render รายละเอียดรายงาน
- การ์ดที่เลือกมีสถานะ accessible และหน้าอื่นไม่ render พร้อมกัน
- เปลี่ยนตัวกรองทำให้รายงานรอการกดแสดงใหม่
- ตัวรวมรายงานส่ง event IDs ที่ถูกต้องสำหรับเลขไมล์ต้นและปลาย
- validation ยอมรับค่าที่ถูกต้องและปฏิเสธเลขไมล์ปลายต่ำกว่าต้น
- authorization ยอมรับ `admin` และ `acc.ap@hillkoff.com` ใน role `accounting`
- authorization ปฏิเสธ sales, accounting อื่น และอีเมลนอกโดเมน
- audit patch เก็บค่าเดิม ค่าใหม่ เหตุผล และผู้แก้ครบถ้วน

### Integration and Rules Tests

- API ปฏิเสธ request ที่ไม่มี token หรือไม่มีสิทธิ์
- transaction ปฏิเสธ event ที่หายหรือเปลี่ยนแปลงระหว่างแก้
- accounting ยังคงเขียน `vehicle_usage_events` และ audit collection โดยตรงไม่ได้

### Release Gate

- `npm run check`
- `npm run test:rules`
- ตรวจ visual ที่ desktop, tablet และ mobile
- ตรวจว่า production build สำเร็จ
- ตรวจ diff และ stage เฉพาะไฟล์ในขอบเขต

## Rollback

- UI rollback: คืน component และ CSS ของเมนูรายงานเป็นเวอร์ชันก่อนหน้า
- API rollback: ปิด route แก้เลขไมล์โดยไม่กระทบ API อ่านรายงาน
- Data rollback: ใช้ audit record เพื่อคืนค่าเดิมของ event ที่แก้แต่ละรายการ
- ไม่มี schema migration ที่ต้องย้อนกลับ
