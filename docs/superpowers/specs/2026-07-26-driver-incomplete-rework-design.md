# Driver Incomplete Delivery Rework Design

## Goal

ให้คนขับระบุว่าสินค้าครบหรือไม่ครบและบันทึกหมายเหตุก่อนแนบรูป/แชร์ LINE โดยกรณีสินค้าไม่ครบต้องกลับเข้ากระบวนการเตรียมสินค้าเดิมตามเส้นทางของออเดอร์ พร้อมให้ฝ่ายขาย สโตร์ และห้องแพ็คเห็นหมายเหตุงานแก้ไขชัดเจน

## Scope and compatibility

- เปลี่ยนเฉพาะการปิดงานออเดอร์บริษัทที่คนขับรับอยู่แล้ว
- ออเดอร์ที่เลือก “ครบ” ยังปิดเป็น `ส่งสำเร็จ` และ `queueStatus: completed` เหมือนเดิม
- ไม่เปลี่ยน flow งานวิ่ง, Grab, รับหน้าร้าน, ต่างจังหวัด หรือการตรวจสโตร์/แพ็คเดิม
- ใช้ `workflowType` เดิมเพื่อแยก `store_route` และ `direct_pack`

## Workflow

1. คนขับถึงปลายทาง เลือก “สินค้าครบ” หรือ “สินค้าไม่ครบ” และกรอกหมายเหตุ
2. เมื่อข้อมูลครบแล้วจึงถ่ายรูป POD และแชร์ LINE
3. ถ้าครบ: ปิดงานเดิม
4. ถ้าไม่ครบและเป็น `store_route`: ตั้งงานแก้ไขรอสโตร์ สโตร์เห็นงานแก้ไขก่อน และห้องแพ็คเห็นประกาศรอการแก้จากสโตร์
5. ถ้าไม่ครบและเป็น `direct_pack`: ข้ามสโตร์ ตั้งงานแก้ไขรอห้องแพ็คโดยตรง
6. เมื่อแก้และตรวจผ่านตาม flow เดิม ออเดอร์กลับสถานะพร้อมเข้าคิวคนขับใหม่

## Data contract

งานแก้ไขใช้ฟิลด์ additive: `reworkRequired`, `reworkRoute`, `reworkStatus`, `reworkNote`, `reworkReportedAt`, `reworkReportedBy`, `deliveryCompleteness` และ `driverNote` เดิม โดยไม่ลบข้อมูลการส่งเดิมหรือ workflow history

## Visibility

- ฝ่ายขาย: แสดงในหน้าเตรียมออเดอร์เชียงใหม่และหน้า Sales พร้อมป้ายสีแดงและหมายเหตุคนขับ
- สโตร์: แสดงเฉพาะ `store_route` และเป็นงานที่ต้องแก้ไข
- ห้องแพ็ค: แสดงทั้งสองเส้นทาง; `store_route` แสดงเป็นงานรอสโตร์ก่อน ส่วน `direct_pack` แสดงเป็นงานรอแพ็คโดยตรง
- ป้ายงานแก้ไขยังแสดงจนกว่ากระบวนการตรวจและส่งกลับเข้าคิวใหม่เสร็จ

## Verification

- ทดสอบ pure routing/rework policy สำหรับสองเส้นทาง
- ทดสอบ unit suite, lint และ production build
- ตรวจ diff ให้มีเฉพาะไฟล์ของฟีเจอร์และเอกสารแผน ไม่แตะไฟล์ผู้ใช้ที่ไม่เกี่ยวข้อง
