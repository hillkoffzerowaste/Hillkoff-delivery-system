# ห้องแพ็คช่วยคีย์ออเดอร์ซ้ำและลดข้อบังคับก่อนเริ่มงานคนขับ

## เป้าหมาย

ให้ห้องแพ็คช่วยคีย์งานได้ต่อเนื่องเมื่อเจอลูกค้าที่มีออเดอร์อยู่แล้ว โดยใช้ออเดอร์เดิมที่ยังแก้ได้เป็นแหล่งข้อมูลล่าสุดและส่งกลับเข้าคิวคนขับได้ทันที พร้อมเปิดให้ห้องแพ็คเพิ่มลูกค้าใหม่จากหน้าคีย์ออเดอร์ได้เอง โดยไม่บังคับคนขับกรอกเลขไมล์หรือทำแบบประเมินรถก่อนเข้าใช้งานแอพ

## ขอบเขตและเงื่อนไขที่ตกลง

- ใช้กับการช่วยคีย์จาก role `pack` และออเดอร์คนขับบริษัทเท่านั้น
- ออเดอร์ซ้ำที่แก้ทับได้ต้องเป็นออเดอร์ของ `serviceDate` วันนี้ และยังไม่มีการรับงานจากคนขับ (`driverId` ว่าง, `acceptedAt` ว่าง และไม่อยู่ในสถานะ `กำลังส่ง`/`กำลังจัดส่ง`)
- ถ้าออเดอร์ของวันนี้ถูกคนขับรับแล้ว ให้ตอบปฏิเสธแบบไม่แก้ข้อมูล เพื่อไม่ให้เกิดงานซ้ำกับคนขับที่กำลังถือออเดอร์อยู่
- ออเดอร์คนละวันไม่ถูกแก้ทับและไม่ถูกใช้เป็นตัวบล็อกการช่วยคีย์ครั้งใหม่
- เมื่ออัปเดตออเดอร์เดิมสำเร็จ ให้ใช้ข้อมูลล่าสุดจากฟอร์ม, บันทึกประวัติการช่วยคีย์ และ refresh สัญญาคิวคนขับ (`driverQueueDate`, `queuedAt`, `queueStatus`, `status`) ให้กลับไปอยู่คิวคนขับทันที
- ไม่เปลี่ยน flow ของ Grab, รับหน้าร้าน, ต่างจังหวัด หรือออเดอร์ที่มีคนขับรับไปแล้ว
- เลขไมล์เริ่มต้นและแบบประเมินรถเป็นตัวเลือกเสริม คนขับเข้าแอพและทำงานได้โดยยังไม่กรอก; หากเลือกบันทึกภายหลัง ฟอร์ม/API ยังตรวจข้อมูลที่จำเป็นของรายการนั้นตามเดิม

## การออกแบบ

### 1. การตรวจซ้ำและอัปเดตออเดอร์แบบ transaction เดียว

ขยาย policy ใน `lib/packAssistOrder.js` ให้ระบุได้ว่าออเดอร์ใดเป็น duplicate ของวันนี้ที่แก้ได้ และแยกกรณีออเดอร์วันนี้ที่ถูกคนขับรับแล้วออกมาเป็น error ที่ผู้ใช้เข้าใจได้

ใน `app/api/orders/create/route.js` เมื่อ role เป็น `pack`:

1. สร้างข้อมูลล่าสุดจากฟอร์มตาม validation เดิม
2. อ่านออเดอร์ของ `customerId` ภายใน transaction
3. ถ้ามีออเดอร์วันนี้ที่คนขับรับแล้ว ให้ยกเลิก transaction ด้วย HTTP 409 โดยไม่เขียนข้อมูล
4. ถ้ามีออเดอร์วันนี้ที่ยังไม่ถูกรับ ให้เขียน patch เฉพาะข้อมูลลูกค้า/งาน/เลขใบสั่งจอง/หมายเหตุล่าสุดลงออเดอร์เดิม, เพิ่ม `workflowHistory` และ activity ที่ระบุผู้ช่วยคีย์, ตั้ง `packStatus: "checked"` และใช้ `buildDriverQueuePolicyPatch(now)` เพื่อส่งเข้าคิวคนขับ
5. ถ้าไม่พบ duplicate ที่เข้าเกณฑ์ ให้สร้างออเดอร์ใหม่ตาม flow เดิม

การอัปเดตต้องคง `id`, `createdAt`, review token, ประวัติการส่ง และข้อมูล audit เดิมไว้ ไม่รีเซ็ตงานที่จบแล้ว และไม่อนุญาตให้ client เลือก order id ของรายการอื่นมาเขียนทับ

### 2. ลูกค้าใหม่จากห้องแพ็ค

- เพิ่ม `pack` ใน allowlist ของ `POST /api/customers/upsert`
- แสดงฟอร์มลูกค้าใหม่ใน urgent-order modal สำหรับ role `pack` โดยใช้ `saveCustomer` และ duplicate-phone confirmation ที่มีอยู่ร่วมกับฝ่ายขาย/สโตร์
- หลังบันทึกสำเร็จ เลือกลูกค้าใหม่ให้ฟอร์มออเดอร์ทันที; การเขียนยังผ่าน API route และ transaction เดิม ไม่ให้ client เขียน Firestore ตรง

### 3. ยกเลิกการบังคับรถ/เลขไมล์ก่อนใช้แอพ

- ลบ modal overlay ที่ขวางคนขับเมื่อยังไม่มี `dailyVehicleStart`
- คงแท็บ “บันทึกการใช้รถ” และ “ตรวจรถประจำวัน” ให้กรอกภายหลังได้
- เอา guard ที่บังคับให้เริ่มใช้รถ/กรอกเลขไมล์ก่อนส่งแบบประเมินออกจากระดับการเข้าใช้งานแอพ แต่เมื่อกดบันทึกแบบประเมินหรือ event รถ ให้ validation ของรายการนั้นทำงานตามเดิม
- ปรับข้อความ SOP/UI ให้สื่อว่าเป็นรายการเสริมและสามารถกลับมากรอกภายหลังได้ ไม่กล่าวว่าเป็นเงื่อนไขก่อนเข้าแอพ

## การทดสอบและการตรวจรับ

- เพิ่ม unit tests ของ pack-assist policy สำหรับ: วันนี้และยังไม่รับแก้ได้, วันนี้รับแล้วปฏิเสธ, คนละวันไม่บล็อก, และ queue patch ใช้วันที่/เวลาล่าสุด
- เพิ่ม route tests ของ `orders/create` สำหรับ transaction update/requeue, ไม่แก้เมื่อ driver รับแล้ว, และสร้างใหม่เมื่อ duplicate เป็นคนละวัน
- เพิ่ม route test ให้ role `pack` upsert ลูกค้าใหม่ได้ และยังคงป้องกัน duplicate ชื่อลูกค้า
- เพิ่ม regression test/contract assertion ว่า `app/page.jsx` ไม่มี startup vehicle modal gate และ assessment/odometer เป็น optional ที่ระดับ workspace
- รัน `npm run lint`, `npm test`, `npm run build`; เปิด dev server ตรวจ urgent-order modal ของ pack และหน้าคนขับจริง

## ผลกระทบและความเสี่ยง

- การเขียนออเดอร์ซ้ำและ booking registry ต้องอยู่ใน transaction เดียวเพื่อป้องกันสองเครื่องช่วยคีย์พร้อมกัน
- ออเดอร์ที่คนขับรับแล้วจะไม่ถูก reset หรือย้ายคิวโดยเด็ดขาด
- ไม่แก้ Firestore Rules, indexes, environment variables, migration หรือ production deployment ในงานนี้
- worktree มีการแก้ค้างก่อนเริ่มงาน จึงต้อง stage/commit เฉพาะไฟล์ของ feature นี้และไม่ทับ diff เดิม
