# ผลตรวจแบบด้านธุรกิจ

ผู้ตรวจ: exec-reviewer · 11 พฤศจิกายน 2569

ผลตรวจต้นแบบก่อนลงโค้ด: ต้องแก้ตรรกะใน implementation ก่อน release ต้นแบบใช้ข้อมูลตัวอย่างและไม่ใช่โค้ดที่จะนำขึ้น production

| ระดับ | ประเด็นที่ต้องตรวจ |
| --- | --- |
| สูง | closed ไม่เท่ากับรับครบ แยก fulfilled/cancelled/exception/unknown |
| สูง | ค้างศูนย์ไม่ยืนยันรับครบ ต้องแยกรับครบ/บางส่วน/ยังไม่รับ/ยกเลิก/ข้อมูลไม่พอ ไม่รวมปริมาณต่าง SKU/หน่วย |
| สูง | drill-down ของกราฟรายบุคคลต้องใช้ชุดเคสเดียวกับกราฟ ไม่ย้อนกลับไปทั้งทีม |
| กลาง | กิจกรรมปิดต้องนับจาก history ตาม actor/วันเหตุการณ์ รองรับเปิดใหม่ปิดซ้ำและ actor ไม่ทราบ |
| กลาง | แหล่งรอใช้ชนิดจริง ไม่อนุมานจากชื่อ supplier หรือถือว่าไม่มี supplier เป็นคลัง PO/จัดสรรไม่เท่ากับรับแล้ว |
| กลาง | แต่ละกราฟระบุฐานวันเอกสาร/วันพบปัญหา/วันกิจกรรม ส่วนค้างปัจจุบันข้ามช่วงไม่ใช่ historical snapshot |

คะแนนแบบ: ถูกต้อง 3/5 ครบถ้วน 4/5 ทำได้จริง 4/5 ความเสี่ยง 3/5 เฉพาะเจาะจง 4/5 ชัดเจน 4/5 ข้อจำกัด: เป็นผลตรวจแบบและเกณฑ์ ยังไม่รับรองโค้ด ต้องตรวจ implementation และผลเทสต์จริงก่อนปล่อย

ส่งประเด็นทั้งหมดให้ dev-lead ระหว่างพัฒนาแล้ว รายงานนี้บันทึกโดยผู้ประสานงานจากผลตรวจ read-only ของ exec-reviewer

## ผลตรวจ implementation รอบสุดท้าย

exec-reviewer ตรวจโค้ดจริงและรัน storeOperational.test.js ผ่าน 7/7 แล้ว ทั้ง 6 ประเด็นเดิมแก้ครบ ไม่พบ must-fix คงเหลือในขอบเขตนี้: partition การปิด/การรับถูกต้อง, drill-down ใช้ part.rows จาก scope เดียวกัน, กิจกรรมใช้ history/actor, แหล่งรอใช้ allocation.kind, และฐานเวลาระบุแยกชัด

ข้อจำกัด: รับรองความหมายข้อมูลจากโค้ดและ unit tests ไม่รับรองความครบถ้วนข้อมูล production การปล่อยยังต้องผ่าน npm run check ล่าสุดและการตรวจ rollout ของ root
