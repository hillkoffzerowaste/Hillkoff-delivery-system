# Store Operations Center — แบบระบบงานสโตร์
วันที่ 11 พฤศจิกายน 2569 · ข้อเสนอเพื่อพิจารณา ยังไม่ใช่นโยบายหรือระบบที่พัฒนาแล้ว

## ข้อเสนอสำหรับผู้จัดการ
เปลี่ยนจุดเริ่มจากกราฟผลงานเป็นคำถาม “วันนี้อะไรติด ใครรับผิดชอบ และต้องทำอะไรต่อ” โดยมีศูนย์ปฏิบัติการสโตร์โมดูลเดียว ใช้เอกสารและทะเบียนเคสเดิมเป็นแหล่งข้อมูลหลัก กราฟเป็นเครื่องมือเจาะตรวจ ไม่สร้าง dashboard ซ้ำอีกชุด
แนะนำหน้าเดียวรวมคิวพร้อมหน้ารายละเอียดเฉพาะงาน มากกว่าหน้ารายงานล้วนซึ่งยังต้องค้นหางานเอง หรือ control tower ทั้งบริษัทซึ่งต้องเชื่อมข้อมูลที่ระบบยังไม่มี ขอบเขตนี้ทำได้ใกล้ระบบปัจจุบันและไม่เปลี่ยน flow คนขับ
สมมติฐาน: รอบส่งบริษัท 11:00 และ 15:00 ใช้แสดงบริบทได้ แต่ยังไม่มีหลักฐานว่าทุกงานสโตร์มีรอบส่งกำหนดไว้ จึงห้ามผูกเอกสารกับรอบโดยเดา และเวลาเหล่านี้ไม่ใช่เวลา cut-off

## โครงสร้างไม่เกิน 6 หน้าในโมดูลเดียว
| หน้า | คำถามหลักและเนื้อหา | การกระทำ |
|---|---|---|
| ศูนย์วันนี้ | งานต้องตัดสินใจ คิวมีเจ้าของ/ไร้เจ้าของ กำหนดวันนี้/เลยกำหนดที่บันทึกไว้ งานรอแหล่งภายนอก ความพร้อมข้อมูล | เปิดรายละเอียด มอบหมายผ่าน flow เดิม เปิดหน้าต้นทาง |
| คิวงาน | เอกสาร booking/online/transfer/audit และเคส แยกประเภทและหน่วย ไม่รวมเป็นยอดงานเดียว | กรองฉัน/ทีม/สาขา/ประเภท/สถานะ เจาะเอกสารหรือเคสเดิม |
| เคสและสินค้าขาด | เคสเดิม รายการขาด ปริมาณค้าง หน่วย แหล่งรอ PO ETA ผู้ติดตาม เหตุการณ์ล่าสุด | รับบางส่วน อัปเดตการติดตาม มอบหมาย ปิดพร้อมเหตุผลตามสิทธิ์เดิม |
| ทีมและภาระงาน | งานเปิดต่อคน อายุคิว ประเภทงาน งานรอภายนอก งานไร้เจ้าของ และกิจกรรมที่ทำจริง | เจาะคิวรายคน ช่วยหัวหน้าจัดงาน ไม่จัดอันดับพนักงานจากยอดดิบ |
| ส่งต่องาน | งานที่มีหลักฐานพร้อมส่งต่อ/รอรับช่วง/ถูกส่งกลับ พร้อมลิงก์ห้องแพ็คหรือ delivery ที่มีอยู่ | เปิดหน้ารับช่วงเดิม แสดงสิ่งขาด ไม่สร้างสถานะปลายทางหรือปุ่มคนขับใหม่ |
| ผลงานและคุณภาพข้อมูล | เอกสาร เคส กิจกรรม และ backlog แยกแกนเวลา พร้อมข้อมูลไม่ครบ/เวลาปรับปรุง | เจาะรายการ ส่งออกรายงานเดิม และอ่านข้อจำกัด |

ทุกหน้ารักษาตัวกรองสาขา/คลัง/เจ้าของและลิงก์กลับ รายการปฏิบัติงานปัจจุบันใช้สถานะปัจจุบันเสมอ ส่วนวันที่หรือช่วงวันที่ต้องระบุชัดว่ากรองวันเอกสาร วันพบปัญหา หรือวันกิจกรรม ไม่ใช้ตัวกรองวันที่เดียวเปลี่ยนความหมายเงียบ ๆ
ศูนย์วันนี้ประกอบด้วยแถบเวลาข้อมูลและขอบเขต → ประเด็นต้องตัดสินใจ → คิวงานที่ทำต่อได้ → สิ่งที่รอผู้อื่น → รายละเอียดข้างจอ กราฟทีมย้ายไปหน้าทีม/ผลงาน บนมือถือแสดงชื่อปัญหา เจ้าของ วันนัด และปุ่มเปิดก่อนรายละเอียดรอง

## จังหวะทำงานประจำวัน
| จังหวะ | ผู้รับผิดชอบตามหน้าที่ | วิธีใช้และผลลัพธ์ |
|---|---|---|
| เริ่มวัน | หัวหน้าสโตร์ | ตรวจข้อมูลล่าสุด งานค้าง งานไร้เจ้าของและวันนัดวันนี้ เลือกงานสำคัญจากผลกระทบที่ยืนยันได้และมอบหมาย |
| ระหว่างวัน | ผู้รับผิดชอบงาน | ทำจากคิวของตน บันทึกสิ่งที่ทำจริง เหตุรอ หลักฐานรับบางส่วน และวันติดตามถัดไป |
| เตรียมแต่ละรอบ | สโตร์ร่วมผู้รับช่วง | ดูงานที่มีรอบกำหนดชัด ตรวจหลักฐานพร้อมส่งต่อ เปิด flow ห้องแพ็คเดิม งานไม่มีรอบอยู่กลุ่ม “ยังไม่ระบุรอบ” |
| เมื่อรอบเปลี่ยน/เกิดเหตุ | หัวหน้ากับเจ้าของเคส | ตรวจรายการติดขัดและกระทบรอบที่ยืนยันแล้ว ปรับการติดตาม/มอบหมาย ไม่ย้ายรอบหรือเปลี่ยนคำมั่นลูกค้าอัตโนมัติ |
| ปิดวัน | หัวหน้าสโตร์ | ตรวจงานค้างใหม่และเก่า แยกรับครบ/ยกเลิก/ข้อยกเว้น ทุกงานค้างควรทราบเจ้าของ เหตุรอ และสิ่งที่จะทำต่อ สรุปรายงานเดิม |

ไม่ตั้ง SLA ใหม่จากอายุงาน: งาน “เลยกำหนด” หมายถึงเลย ETA หรือวันนัดที่มีผู้บันทึกจริงเท่านั้น ถ้าไม่ระบุให้ใช้ “ไม่มีวันนัด” อายุงานเป็นข้อมูลประกอบ การแจ้งเตือนก่อนรอบและ cut-off ต้องให้เจ้าของกระบวนการยืนยันก่อนเปิดใช้

## กฎคิวและการแนะนำงาน
ใช้กฎอธิบายได้ แสดงเหตุผลใต้ทุกรายการ เรียงกลุ่มต่อไปนี้แล้วเรียงวันนัดเก่าสุด/วันพบปัญหาเก่าสุด ไม่แต่งคะแนนความรุนแรงรวม
1. งานมี blocker และยืนยันว่ากระทบรอบ/กำหนดงานที่ระบุ: ให้เจ้าของเปิดรายละเอียดและหัวหน้าตัดสินใจ ข้อมูล blocker และรอบต้องเชื่อมเพิ่มก่อนใช้งานกฎนี้
2. วันนัดหรือ ETA ที่ระบุเลยแล้ว และงานยังไม่เสร็จ: “ติดตามแหล่งรอและปรับวันนัด” พร้อมวันที่อ้างอิง
3. งานไร้เจ้าของ: “หัวหน้าระบุผู้รับผิดชอบ” ไม่สุ่มชื่อหรือสืบจากผู้คีย์
4. งานค้างที่ไม่มีวันติดตาม/แหล่งรอ หรือจำนวนยังไม่ระบุ: “เติมข้อมูลที่ขาด” ไม่ตีความว่าไม่มีปัญหา
5. งานถึงวันนัดวันนี้และงานเปิดอื่น ๆ: เปิดคิวปกติและเรียงอายุ

สถานะรอ supplier ไม่ทำให้เรื่องหายจากคิว เจ้าของเคสยังรับผิดชอบการติดตาม แยกคนทำเอกสาร เจ้าของเคส และผู้ติดตามแหล่งรับ ไม่เหมารวมเป็นคนเดียว การเปลี่ยนเจ้าของต้องมีประวัติ; หัวหน้าจัดการรายการไร้เจ้าของตามสิทธิ์เดิม หาก API ยังไม่มีสิทธิ์นั้นให้เป็นข้อเสนอรอยืนยัน ไม่ขยาย role เอง

## สินค้าขาดและการส่งต่อ
ใช้ canonical case เดิมจาก sourceType + sourceId เสมอ หนึ่งเคสอาจมีหลายสินค้าและหลายแหล่งรับ แสดงยอดต้องรับ รับยืนยัน ยกเลิก และค้างแยกกัน ค้าง = max(0, ต้องรับ − รับยืนยัน − ยกเลิกที่มีเหตุผล) รวมปริมาณได้เฉพาะ SKU และหน่วยเดียวกัน ห้ามรวม kg กับถุง หรือข้ามสินค้ามาเป็น KPI จำนวนชิ้น
เลข PO และ ETA เป็นหลักฐานติดตาม ไม่ใช่ stock พร้อมใช้ การบันทึก PO/จัดสรรไม่ทำให้รับครบ รับบางส่วนยังค้าง แหล่งรอหลายแหล่งต้องไม่จัดสรรเกินค้าง เปิดใหม่ใช้เคสเดิม ประวัติปิดรับครบ/ยกเลิก/ข้อยกเว้นยังต้องแยก
การส่งต่อแสดงเฉพาะข้อมูลที่ต้นทางหรือปลายทางบันทึกจริง หากยังไม่มี receiver acknowledgement ให้แสดง “ยังไม่มีหลักฐานรับช่วง” ไม่อ้างว่าส่งต่อสำเร็จ วันที่ส่งต่อและรับช่วงต้องเป็นเหตุการณ์จริง ไม่ใช้วันที่เอกสารแทน ห้ามปิดเคสเพียงเพราะเปิดหน้าห้องแพ็ค

## พจนานุกรมตัวเลข
| ตัวเลข | หน่วยและฐานเวลา | ข้อจำกัด |
|---|---|---|
| เอกสารในช่วง | เอกสารไม่ซ้ำต่อ sourceType + sourceId ตามวันเอกสาร | booking/online/transfer/audit แยกประเภท งานจัดเอกสารและคีย์แยกบทบาท |
| รายการ Audit | รายการตามนิยามในระบบเดิม | ไม่รวมกับเอกสารหรือจำนวนสินค้า ต้องยืนยัน grain ของข้อมูลก่อนเปลี่ยนชื่อ |
| เคสเกิดในช่วง | caseId ไม่ซ้ำตามวันพบปัญหา; แยกสถานะปัจจุบันของชุดเดียวกัน | วันประมาณจากข้อมูลเก่าติดป้าย ไม่ใช่ปริมาณเคสที่เคยมีทั้งหมด |
| กิจกรรมปิดในช่วง | เหตุการณ์ปิดรับครบตามเวลาปิดจริง แสดง caseId ไม่ซ้ำควบคู่จำนวนเหตุการณ์ | เปิดใหม่แล้วปิดซ้ำได้ จึงห้ามเท่ากับเคสเกิดในช่วง; ยกเลิก/ข้อยกเว้นแยก |
| งานค้างสะสมขณะนี้ | เคสเปิดปัจจุบันรวมก่อนช่วงที่เลือก | ไม่เปลี่ยนเป็นค้างสิ้นเดือนเมื่อเลือกวันที่ย้อนหลัง |
| อายุเคสเปิด | เวลาปัจจุบัน − วันพบปัญหา | วันประมาณต้องระบุ เปิดใหม่ไม่รีเซ็ตอายุเดิม; ช่วงเปิดล่าสุดเป็นอีกตัวเลขหากมี history |
| เลยวันนัด | งานเปิดที่วันนัดที่ระบุอยู่ก่อนเวลาที่ดู | แยก ETA แบบวันกับเวลานัด; ไม่ระบุไม่เท่ากับตรงเวลา |
| ภาระงานรายคน | เคส/เอกสารเปิดแยกประเภทพร้อมอายุและเหตุรอ | ไม่ใช่ชั่วโมงทำงาน ความสามารถ หรือ capacity ที่เหลือ |
| พร้อม/รับช่วง | จำนวนงานตามหลักฐานต้นทาง/ปลายทาง | ใช้ได้เมื่อมี field และเหตุการณ์ที่เชื่อมกันแล้ว |

ทุกยอดกดดูรายการฐานได้ ใช้ขอบเขตและแหล่งข้อมูลเดียวกัน ไม่เฉลี่ยเปอร์เซ็นต์รายคนเป็นเปอร์เซ็นต์ทีม ไม่แสดงอัตราปิดครบย้อนหลังจนกว่าฐาน cohort และความครบข้อมูลจะเพียงพอ กรณีอ่านเกินเพดานหรือโหลดไม่สำเร็จให้แสดงข้อผิดพลาดและลองใหม่ ห้ามแสดงบางส่วนเป็นยอดทั้งหมด

## ข้อมูลที่มีแล้ว / ต้องเพิ่ม / ต้องเชื่อม
| สถานะ | ข้อมูล | วิธีใช้/ข้อจำกัด |
|---|---|---|
| มีแล้วตาม README ปัจจุบัน | เอกสาร 4 ประเภท กราฟทีม/รายคน canonical cases รายการสินค้า รับบางส่วน หลายแหล่ง supplier/PO/ETA owner/history วันเอกสารย้อนหลังและเหตุผล | ใช้ API และการคำนวณกลางเดิม ตรวจ field mapping ก่อนพัฒนา ไม่สร้างทะเบียนขนาน |
| ต้องตรวจ field ที่มี ก่อนเพิ่ม | nextFollowUpAt, blockingReason, affectedDispatch, handoff evidence, ผู้ติดตามระดับแหล่งรับ | เป็นความต้องการเชิงธุรกิจ ไม่ยืนยันว่าปัจจุบันครบ; เพิ่มเฉพาะส่วนที่ตรวจว่าไม่มี |
| ต้องเชื่อม | รหัสงานจากเอกสารสโตร์ไปออเดอร์/ห้องแพ็ค/ปลายทาง เหตุการณ์ส่งและรับช่วง | deep link ทำก่อน ข้อมูลความพร้อมและการรับช่วงทำเมื่อ mapping ชัด ไม่จับคู่ด้วยเลขเอกสารล้วน |
| ต้องเชื่อมภายหลัง | ยอด stock จริง lot/BBF PO จริงและการรับของจากระบบเจ้าของ | ต้องกำหนดแหล่งจริงและรอบ sync ก่อน; ไม่ใช้ tracker สร้าง available stock หรือข้อเสนอจัดซื้ออัตโนมัติ |
| มีข้อจำกัด | เคสเก่าปิดก่อนทะเบียน วันพบปัญหาโดยประมาณ ประวัติไม่ครบ | แสดงป้ายความครอบคลุมและวันข้อมูลล่าสุด ไม่สร้างรายงาน as-of หรือ trend ค้างย้อนหลังจากสถานะปัจจุบัน |

## แผนทำและเกณฑ์รับงาน
**MVP:** รวมทางเข้าหลัก 6 หน้าภายในโมดูลเดียว ยุบทางเข้ากราฟซ้ำโดยคงรายงานเดิมเข้าถึงได้ ทำศูนย์วันนี้จากข้อมูลจริง คิวมีเจ้าของ/ไร้เจ้าของ/เลย ETA ทะเบียนเคสเดิม และลิงก์หน้าส่งต่อ ยืนยันนิยามตัวเลขกับสโตร์ก่อนพัฒนา ผู้รับผิดชอบคือหัวหน้าสโตร์รับแบบธุรกิจและทีมพัฒนาทำ mapping/API/UI หลังอนุมัติแบบ ไม่กำหนดวันส่งมอบจนตรวจขอบเขต field และข้อมูลตัวอย่างแล้ว
**ระยะ 2:** เพิ่มวันติดตามและเหตุ blocker ที่ขาด เชื่อม receiver acknowledgement และรอบส่งรายงานจริง ทำแจ้งเตือนตามกฎที่ยืนยันแล้ว; historical snapshot และ stock/PO integration เป็นงานแยกหลังระบุเจ้าของข้อมูล ไม่รวมเป็นเงื่อนไขปล่อย MVP

- เปิดศูนย์วันนี้แล้วระบุเหตุค้าง เจ้าของ และสิ่งที่ทำต่อได้จากรายการเดียว; ทุก action เปิดหน้าหรือทำธุรกรรมที่มีสิทธิ์จริง
- ยอดทุกกราฟ/คิวเจาะแล้วตรงฐานเดียวกัน แยกเอกสาร รายการ เคส เหตุการณ์ และปริมาณ SKU/หน่วยชัด
- ทดสอบวันเอกสารย้อนหลังกับวันพบ/วันปิดจริง เคสเก่าข้อมูลไม่ครบ เปิดใหม่ รับบางส่วน หลายแหล่ง ยกเลิก และไม่มีเจ้าของ โดยไม่สร้างเคสซ้ำหรือปิดครบผิด
- กฎเลยนัดไม่รวมรายการไม่มีวันนัด กฎกระทบรอบไม่ทำงานเมื่อไม่มีหลักฐาน ไม่มีคำแนะนำ stock หรือ PO ที่ระบบไม่รู้
- เลือกช่วงย้อนหลังแล้ว backlog ยังระบุ “ค้างขณะนี้” ไม่มีตัวเลขสิ้นวันที่อ้างจากสถานะปัจจุบัน
- ผู้จัดการตรวจคิวทีมได้โดยไม่ถูกชี้นำให้จัดอันดับคนจากจำนวนเอกสาร; ทีมสโตร์ตรวจเส้นทางเริ่มวัน เตรียมรอบ และปิดวันด้วยสถานการณ์ตัวอย่าง
- มือถืออ่านและเปิดงานได้ สถานะ empty/loading/error/ข้อมูลเกินเพดานแยกชัด ไม่มีรายการสมมติปะปนข้อมูลจริง
- เมื่อพัฒนา ต้องตรวจ lint/unit/build และ browser desktop/mobile รวมกดซ้ำ/เครือข่ายล้มเหลว ไม่เปลี่ยนสิทธิ์หรือ flow คนขับ

## ความเสี่ยงและข้อมูลต้องยืนยัน
ความเสี่ยงหลักคือทำ tracker ให้ดูเหมือน stock จริง ใช้ ETA แทน SLA ใช้ยอดค้างปัจจุบันแทนอดีต และจับคู่งานส่งต่อผิด จึงต้องมีป้ายฐานข้อมูล กฎที่ตรวจสอบได้ และลิงก์อ้างอิงจริง
ก่อนล็อก UI หัวหน้าสโตร์ยืนยันความหมายงานพร้อมส่งต่อ รอบที่ผูกกับงานจริง ผู้มีอำนาจมอบหมาย และวิธีนัดติดตาม ทีมพัฒนาตรวจ field/API ที่มีจริง ส่วนผู้รับช่วงห้องแพ็คยืนยันหลักฐานรับช่วง ระยะออกแบบนี้ไม่เปลี่ยนนโยบาย ไม่มีข้อมูล stock/ต้นทุน/พนักงานหรือ KPI จริงที่แต่งขึ้น
