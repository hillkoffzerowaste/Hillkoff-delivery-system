## 1. หน้ารายงานประจำวันใหม่

แถบบนเลือกวันที่/ช่วงวันที่ พนักงาน และสาขา พร้อมเวลาปรับปรุงข้อมูล

1. KPI จำนวนเอกสาร พนักงานที่มีงาน เคสเกิดในช่วง แก้แล้ว และค้าง
2. กราฟแท่งซ้อนเปรียบเทียบพนักงาน แยกใบสั่งจอง ออนไลน์ ใบโอน และเอกสาร Audit
3. โดนัทสัดส่วนประเภทเอกสารรายคน เลือกคนแล้วดูรายละเอียดได้
4. โดนัทสถานะเคส แยกงานกำลังดำเนินการกับแก้แล้ว พร้อมยอดค้างสะสมแยกต่างหาก
5. ตารางเคสเร่งติดตาม เรียงเก่า/เกินกำหนดก่อน และรายการเอกสารที่กดเจาะจากกราฟ

คงตารางรายละเอียด บันทึกงาน หน้าที่ประจำวัน และข้อความ LINE ใช้สี teal ตามระบบเดิม กราฟต้องมีจำนวนและคำอธิบาย ไม่พึ่งสีอย่างเดียว รองรับมือถือและกรณีไม่มีข้อมูล

จำนวนเอกสาร จำนวนรายการ Audit จำนวนสินค้า และจำนวนเคสเป็นคนละหน่วย ห้ามรวมเป็นยอดเดียว ผลงานจัดเอกสาร งานคีย์ และงานแก้ปัญหาต้องแยกบทบาท ไม่ใช้ยอดรวมจัดอันดับความสามารถโดยตรง ข้อมูลไม่ทราบผู้ทำให้แสดงแยก

## 2. ทะเบียนเคสและวิเคราะห์ปัญหา

- ระยะแรกหนึ่งเอกสารต้นทางเป็นหนึ่งเคส มีหลายรายการปัญหาภายในได้ ใช้ sourceType + sourceId เป็นตัวเชื่อมไม่ใช้เลขเอกสารล้วน เปิดใหม่ใช้เคสเดิม
- เก็บรหัสเคส ประเภทปัญหา เอกสารต้นทาง วันพบปัญหา ผู้รับผิดชอบ สาเหตุ การแก้ไข และประวัติ
- รายการสินค้าเก็บชื่อ/รหัส/หน่วย จำนวนต้องรับ รับแล้ว และค้าง รองรับปัญหาขาด ผิด ชำรุด และปัญหาระดับเอกสารที่ไม่มี SKU
- สถานะเปิด/กำลังดำเนินการ/ปิด/เปิดใหม่ ปิดแบบรับครบต้องแยกจากปิดยกเลิกหรือข้อยกเว้นที่มีเหตุผล
- ข้อมูลเก่าที่มีแค่หมายเหตุให้แสดงข้อความเดิมและ “ยังไม่ระบุรายการสินค้า” ไม่เดาว่าศูนย์หรือครบ
- วิเคราะห์จำนวนเคสตามสาเหตุ สินค้า สาขา แหล่งที่รอ อายุเคส และเคสเกินกำหนด หากข้อมูลยังไม่ระบุให้แสดงกลุ่มไม่ทราบ

นิยามตัวเลข: เคสเกิดในช่วง = เคสที่ยังเปิด + เคสที่ปิด ของเคสชุดเดียวกัน ณ เวลาที่ดู ส่วนกิจกรรมปิดเคสในช่วงนับตามวันที่แก้จริง อาจเป็นเคสเก่า จึงต้องแยก KPI; ยอดค้างสะสมรวมเคสก่อนช่วงด้วย การยกเลิกแสดงแยกจากแก้สำเร็จ

## 3. โมดูลสินค้าขาด / ติดตามจัดซื้อ

เพิ่มแถบโมดูลเดียว มีตัวกรองรอจัดซื้อ/สั่งแล้วรอรับ/รอโอนภายใน/รับบางส่วน/ครบ/ยกเลิก ดึงจากเคสเดิมเพื่อลดการคีย์ซ้ำ

แต่ละรายการแสดงสินค้าขาดเท่าไร รอที่สาขา/คลัง/supplier ใด ผู้ติดตาม เลข PO หรือเอกสารอ้างอิง วันที่คาดรับ และวันติดตามล่าสุด รายการเดียวรอได้หลายแหล่งโดยแยกจำนวนต่อแหล่ง

ยอดค้าง = max(0, จำนวนต้องรับ - จำนวนรับยืนยัน - จำนวนยกเลิกที่มีเหตุผล) แสดงจำนวนยกเลิกแยก รับเกินต้องแจ้งและตรวจสอบ การจัดสรรจากหลายแหล่งต้องไม่เกินยอดค้าง การมีเลข PO ไม่ทำให้ปิดเคสอัตโนมัติ การรับบางส่วนยังคงยอดค้าง

ระยะแรกเป็นทะเบียนติดตามภายใน อ้างอิง supplier/PO ที่ระบุ ยังไม่ใช่การสร้าง PO ส่ง supplier หรือยอด stock สดจากระบบจัดซื้อ

## 4. คีย์เอกสารย้อนหลัง

- เพิ่มวันที่เอกสารในฟอร์มสร้างและแก้ไข ใช้เลือกวันเก่าได้ แยกจากวันที่กรองหน้ารายการ
- serviceDate เป็นวันที่เอกสาร ส่วน createdAt/updatedAt เป็นเวลาจริงจาก server เก็บผู้คีย์และเหตุผลย้อนหลัง
- หัวเลขใบโอนอิงเดือน/ปีของวันที่เอกสาร ส่วนใบขอโอนอ้างอิงอาจเป็นคนละเดือน ต้องเลือกแยกได้
- กันเลขซ้ำตามขอบเขตทะเบียนเลขเดิม การเปลี่ยนเลข/วันที่/สาขาที่กระทบกุญแจทะเบียนต้องจองใหม่และปล่อยเดิมใน transaction เดียว ตรวจเจ้าของทะเบียนและป้องกันกดซ้ำ
- ไม่เปลี่ยนสิทธิ์ของ role หรือนโยบายช่วงย้อนหลังโดยเดา หากต้องจำกัดช่วงหรือเพิ่มผู้อนุมัติต้องตกลงเป็นข้อกำหนดแยก
- วันที่เอกสารย้อนหลังไม่ทำให้วันรับของหรือวันแก้เคสย้อนหลังตามโดยอัตโนมัติ เก็บเวลาที่เหตุการณ์มีผลและเวลาบันทึกจริงแยกกัน
- รายงานเอกสารย้อนหลังที่แสดงสถานะปัจจุบันต้องติดป้ายให้ชัด รายงานค้าง ณ สิ้นวัน/เดือนต้องคำนวณจาก event history เท่านั้น ช่วงเก่าที่ประวัติไม่พอต้องแจ้งข้อจำกัด ห้ามอ้างว่าเป็น snapshot ที่ถูกต้อง
- หากยอมให้ลงเหตุการณ์ย้อนหลัง รายงานที่คำนวณใหม่ต้องแจ้งว่าเป็นตัวเลขปรับตามข้อมูลย้อนหลัง พร้อมเวลาข้อมูลล่าสุด

## 5. งานพัฒนาและเกณฑ์รับงาน

ลำดับ: ยืนยันชนิดเอกสารและนิยามวันที่ → รองรับ backdate/ทะเบียนเลข → กราฟจากข้อมูลเดิม → ทะเบียนเคส → ติดตามสินค้าขาด → เชื่อมตัวเลขกับ overview

ไฟล์หลัก: `app/components/store/StoreDailyReport.jsx`, `StoreTransferPanel.jsx`, `lib/storeDailyReport.js`, `lib/storeTransfers.js`, `lib/storeSettings.js`, `app/api/store/transfers/route.js`, `app/api/store/daily-report/route.js` และ wiring ใน `app/page.jsx` เพิ่ม validator/API/component สำหรับเคสและสินค้าขาด โดยกำหนดเจ้าของข้อมูลเคสเพียงแหล่งเดียว

สโตร์ยืนยันชนิดเอกสาร ความหมายครบ/ขาด ผู้รับผิดชอบ และรับงาน; ผู้ดูแลจัดซื้อยืนยันขั้นตอนรอ supplier/PO; ทีมพัฒนารับผิดชอบ API, transaction, กราฟ และการตรวจสอบ ไม่ขยายสิทธิ์ผู้ใช้เดิมอัตโนมัติ

เกณฑ์รับงาน:

- ยอดกราฟตรงเอกสารจริงต่อคน ยอดทีมไม่ซ้ำ และข้อมูลไม่ทราบผู้ทำแสดงแยก
- หนึ่งเคสหลายสินค้า รับบางส่วน รอหลายแหล่ง เปิดใหม่ ไม่เพิ่มยอดเคสซ้ำและไม่ปิดครบทั้งที่ยังค้าง
- ตัวเลขเคสในช่วง กิจกรรมแก้ในช่วง และค้างสะสมแยกความหมายชัดเจน ข้อมูลเกินเพดานอ่านต้องไม่แสดงว่าเป็นยอดครบทั้งหมด
- สร้าง/แก้เอกสารย้อนหลังข้ามเดือนและปีได้ตามข้อกำหนด เลขซ้ำถูกปฏิเสธโดยไม่ทิ้งทะเบียนค้าง ข้อมูลพร้อมกันไม่เขียนทับ และ retry ไม่สร้างซ้ำ
- รายงานเก่าและ LINE export ยังทำงาน ถูกสิทธิ์ และไม่รบกวน flow คนขับ
- ตรวจ lint, unit tests, build และเบราว์เซอร์จริง desktop/mobile รวม network failure, disabled state และกดซ้ำ

ขั้นนี้ยังไม่แก้โค้ด ไม่รัน migration/backfill ไม่ deploy และยังไม่ได้รันชุดทดสอบของระบบ การเติมข้อมูลเก่าต้องเสนอ dry-run แยกก่อน
